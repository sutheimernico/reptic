## Offene Fragen (der Kern — hier weitermachen)
1. **Echte Root Cause des Speicher-Bugs unbekannt.** Arbeitshypothese war: v2-Migration wirft
   → `PRAGMA user_version = 2` wird nie erreicht → Migration läuft bei **jedem** Reload erneut
   (Nicos Tunnel reconnectete laut Metro-Logs ständig) → `DELETE FROM exercises` löscht wiederholt,
   während `gyms` via `CREATE TABLE IF NOT EXISTS` überlebt (erklärt "Quakenbrück bleibt, Rest weg").
2. **Diese Hypothese ist NICHT bestätigt.** Meine erste sqlite3-Repro schien sie zu beweisen
   (`DROP TABLE workouts` warf `no such table: workout_exercises`), aber das war ein **Fehler im
   Test-Statement-Splitter**: er verschluckte wegen der `--`-Kommentarzeilen im V2_MIGRATION-String
   das `DROP TABLE IF EXISTS workout_sets`. Mit **korrekt** gesplittetem SQL (Kommentare zeilenweise
   entfernt) wirft der **alte** Migrationscode gar nicht — Migration läuft sauber, `user_version=2`.
3. **Mein Test reproduziert Nicos Symptom NICHT.** Weder alt noch neu lässt sich "zweiter Gym
   speichert nicht" nachstellen — im Test werden Quakenbrück UND Berge UND Bankdrücken gespeichert.
   Also fehlt die eigentliche Fehlerquelle noch komplett.
4. **Wichtige Meta-Lehre:** die gestrige "verifiziert gegen sqlite3"-Aussage (Commit `1bd9e9b`) nutzte
   Python `executescript`, das den `foreign_keys`-Zustand anders behandelt als expo-sqlites `execAsync`
   — nicht faithful. sqlite3-CLI/`executescript` ≠ expo-sqlite-Verhalten. Für DB-Tests künftig:
   statement-by-statement, autocommit, `foreign_keys` explizit setzen, Kommentare sauber strippen.
